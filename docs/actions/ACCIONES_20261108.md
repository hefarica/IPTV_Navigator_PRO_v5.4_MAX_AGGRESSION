## ✅ #4 EJECUTADO — El sobre global ya no declara un perfil que el catálogo no usa

**Defecto medido (§20):** `#EXT-X-APE-LAB-METADATA` declaraba `profile: "P0"` (8K, hdr10plus,
`nlmeans=s=3.0:p=7:r=15`) mientras **20.222 de 21.224 canales (95,3 %) corrían P3 (1080p)**.
Cualquier consumidor del sobre —canonicalizador del VPS, `LabMetadataStore` del APK— recibía
recetas de 8K para un catálogo 1080p.

**Causa:** `generateLabMetadataTag()` tomaba el perfil de `ProfileManagerV9.activeProfileId`
(un ajuste de UI que podía estar en P0 sin relación con el catálogo exportado).

**Arreglo:** el perfil del sobre es ahora el **dominante de los canales que se están exportando**,
y el sobre declara de dónde salió:

```json
{ "profile": "P3",
  "profile_basis": "dominant_of_channels",
  "profile_counts": { "P3": 20222, "P1": 933, "P4": 58, "P5": 11 } }
```

Si no hay canales legibles, cae a `profile_basis: "active_profile"` — **no inventa**.

**Probado** (3 escenarios, arnés `vm` con el LAB v24 real):

| Escenario | Resultado |
|---|---|
| 3 canales P3 + 1 P1, UI en P0 | `profile=P3` · `basis=dominant_of_channels` · `counts={"P3":3,"P1":1}` |
| 1 canal P1, UI en P0 | `profile=P1` · `dominant_of_channels` |
| canales sin perfil | `profile=P0` · `basis=active_profile` · `counts=null` |

**No cambia** ninguna cadena de filtro, ni `EXTINF`, ni las URIs. Solo la cabecera de metadata.
