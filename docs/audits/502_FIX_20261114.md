## 3. El arreglo: admisión ante el proveedor en el JIT

### 3.1 Qué había

`tools/lab/ape-jit/server.js` (desplegado hoy como `/opt/ape-jit/server.js`, `sha256 8e9e663b…`) ya tenía **un** mecanismo de slot:

```js
/* SLOT UNICO: el proveedor solo acepta max_connections=1. No se arranca el
 * ffmpeg nuevo hasta que el anterior haya muerto de verdad. */
const slotOk = await slotAcquire();          // espera a liveKids.size === 0
```

Eso serializa **JIT ↔ JIT**. No dice nada del **operador** (P1/P2) ni del **canary** (P3): con el operador viendo la tele, un zap al JIT abría una **segunda** conexión al upstream. t54 §2 lo dejó escrito: *«el JIT no consulta el gate: puede arrancar con un canary dentro»*.

### 3.2 Qué se añadió

Una puerta **antes del `spawn`** y **después** de `slotAcquire()`:

```js
const admit = providerGateAdmit('jit');
if (!admit.allow) {
  log('START_ABORT', id, 'gate=' + admit.reason + ' (otro propietario del slot; no se abre la conexion)');
  recordStartFailure(id, sdr, sdr720, new Error('PROVIDER_SLOT_BUSY'));
  return;                       // ← NO se spawnea: no hay conexión al proveedor
}
```

`providerGateAdmit()` llama al gate con su API documentada (`provider_gate_decide jit`) y traduce su línea:

| respuesta del gate | decisión del JIT | por qué |
|---|---|---|
| `ALLOW … idle_admit` | **abre** | no hay otro dueño |
| `DENY … player_active` | **NO abre** | el operador está viendo: sería el 2.º dueño |
| `DENY … canary_holds_connection` / `canary_already_live` | **NO abre** | el canary tiene el slot |
| `DENY … player_state_unknown_failclosed` / `canary_state_unknown_failclosed` / `gate_selftest_failed` | **NO abre** | sin poder probar que estamos solos, no se abre |
| `DENY … jit_serving_player_path` | **abre** | **única excepción**, y está razonada: esa razón la dispara **cualquier** ffmpeg del JIT —incluidos los de `liveKids`—. Respetarla sería negarse a sí mismo en cada canal |
| gate ausente | **abre** + `GATE_ABSENT` | sin gate instalado no hay otro dueño al que proteger |
| gate presente pero roto / timeout | **NO abre** (`gate_unavailable` / `gate_timeout`) | fail-closed |

### 3.3 Por qué esto NO degrada

No se sirve la lista a menor resolución ni a menor bitrate: **no se sirve nada distinto**. El motor registra el fallo con el código **`PROVIDER_SLOT_BUSY`**, que viaja al player en `manifest.json:error` con el mismo texto que el motor ya usa para sus fallos de arranque:

```
PROVIDER_SLOT_BUSY: use provider-direct; source unchanged
```

Es decir: se le dice al player «usa tu ruta directa, la fuente no cambia». La imagen que el operador ve **no se toca**.

### 3.4 Observabilidad (sin ella el arreglo sería invisible)

`/health` del JIT ahora publica:

```json
"provider_gate": { "checks": N, "allow": N, "deny": N, "absent": N,
                   "last_reason": "player_active", "last_claimant": "jit", "last_at": "..." }
```

`checks` sube en **cada intento de transcode**; `deny` cuenta las veces que el motor **no** abrió la conexión. Ese contador es el que permite medir el efecto después del deploy sin adivinar.

## 5. El timeout 4 s / 6 s: medido, es de `pulse.php`, y NO se toca

| dato | valor | fuente |
|---|---|---|
| connect / total de nuestro cliente | **4 s / 6 s** | `vps/prisma/api/pulse.php:407-408` (`CURLOPT_CONNECTTIMEOUT => 4`, `CURLOPT_TIMEOUT => 6`) |
| p95 del proveedor | **5,043 s** | citado en el encargo (t53 §4.1 lo usa como referencia) |
| mediana del `rt` de los 502 con estadística | **4,315 s** | t53 §4.1 (n=155, muestra distinta) |
| deadline propio del JIT contra el upstream | **ninguno** | grep sin coincidencias; su upstream es `ffmpeg` con `-reconnect*` |

**Lectura honesta:** con `total = 6 s` y `p95 = 5,043 s`, el deadline solo corta la **cola** (el 5 % más lento). No explica la mayoría de los 502, y la mediana de los 502 (4,315 s) **no llega** al deadline — o sea que **no** se estaban rindiendo por nuestro reloj. Aun así es un defecto real (cortar la cola es cortar el 5 % de las reproducciones lentas).

**Por qué NO lo arreglo aquí:** está en `pulse.php` (dueño **P2**), fuera del fichero que este encargo autoriza (`tools/lab/ape-jit/server.js`), y t54 lo dejó dicho: *«Es el mismo fichero que ya rompió producción una vez; no lo toco, lo señalo»*. Subir el deadline cambia el comportamiento de un owner que comparte slot con el operador: **merece su propia tarea con su propia medición**, no un cambio de rebote dentro de un arreglo del JIT.

## 6. Medición: el ANTES, en la unidad del encargo (502/min y 502 por zap)

Misma fuente (`/var/log/nginx/playlist_access.log` del VPS), misma unidad (502 por minuto), lectura por `ssh`:

| ventana | duración | 502 | **502/min** | fuente |
|---|---:|---:|---:|---|
| 00:00:17 → 02:00:44 (antes del gate) | 120,45 min | 133 | **1,1042** | t53 §2 |
| 02:00:45 → 02:11:42 (con gate) | 10,95 min | 4 | **0,3653** | t53 §2 |
| **00:00:17 → 13:25:53 (fichero actual completo)** | **805,6 min** | **301** | **0,3736** | **medido hoy en esta tarea** |
| ↳ cola 02:11:42 → 13:25:53 | 674,35 min | 164 | **0,2432** | derivado de las dos filas anteriores |

**Lo que esto dice y lo que no:**

- El fichero actual tiene **9.529 líneas y 301 respuestas 502** entre las 00:00:17 y las 13:25:53 UTC. La tasa global (**0,3736/min**) es la misma que la post-gate de t53 (**0,3653/min**): **el gate no bajó la tasa a cero**, exactamente como concluyó t53.
- La **cola** (después del evento de canaries) va a **0,2432/min**, ~4,3× menos que la ventana de t53. **No atribuyo la causa**: pueden ser menos zapping, menos canaries o azar de 11 h. Se reporta como dato, no como efecto de nada.
- **502 por zap: `NO_COMPUTADO`.** t53 §3 ya demostró que esa métrica **no discrimina** (56 hits/min a la misma lista con 0 canaries ⇒ casi todo instante está a <10 s de un zap). No la reintento.

**El DESPUÉS es `NO_COMPUTADO`, y no por pereza:** el arreglo **no está desplegado** (está en el repo, pendiente de CI/CD) y su efecto solo existe mientras el JIT intente transcodificar con otro dueño presente. En el instante de medir:

```
pgrep -c ffmpeg  ->  0        (el JIT no estaba transcodificando)
```

Con 0 ffmpeg vivos, **el JIT no pudo causar ninguno de los 301 del fichero actual en ese instante**, y no hay evidencia per-evento que lo atribuya a él en el pasado. **El arreglo es preventivo sobre un mecanismo demostrado (t54), no una reducción medida.**

**El comando que cierra la medición** (cuando el operador despliegue y reinicie):

```bash
# 1) el proceso tiene el código nuevo (no basta el fichero)
sha256sum /opt/ape-jit/server.js                      # debe dar 8c1a0085…eaec6
curl -s http://127.0.0.1:<puerto-jit>/health | jq .provider_gate

# 2) la tasa, en la misma unidad y desde el mismo log
L=/var/log/nginx/playlist_access.log
awk '$9==502' "$L" | wc -l                            # 502 absolutos
head -1 "$L"; tail -1 "$L"                            # ventana real
# 3) y el contador del arreglo: cuántas veces NO se abrió la conexión
curl -s http://127.0.0.1:<puerto-jit>/health | jq .provider_gate.deny
```

Si `deny` sigue en 0 después de una sesión normal de zapping, el JIT no era el 2.º dueño en ese período — y eso también es un resultado: **el arreglo no habría cambiado nada y el 502 restante es del proveedor**.
