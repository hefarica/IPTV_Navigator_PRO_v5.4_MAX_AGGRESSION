## 1 · EL FALLO: la cola existe pero el usuario de PHP no puede escribirla

Prueba directa, encolando una lista concreta (`APE_PRUEBA_ORDER_OK.m3u8`, que **no** es la más reciente y no estaba cableada) por HTTP:

```text
$ curl -X POST -d 'lista=APE_PRUEBA_ORDER_OK.m3u8&publicar=1' \
       https://iptv-ape.duckdns.org/prisma/api/cablear.php
{"ok":false,"error":"E_COLA_NO_ESCRIBIBLE",
 "motivo":"no se pudo crear el directorio de la cola: /var/lib/ape/cablear (el worker NO puede renombrar el ticket a tomados/ sin el; el ticket no se crea para no dejar un queued eterno)",
 "auth":"heredada"}
HTTP=500
```

**Causa medida, no inferida:**

```text
drwxr-xr-x root:root      /var/lib/ape/cablear
drwxrwxr-x root:root      /var/lib/ape/cablear/cola
drwxrwxr-x root:root      /var/lib/ape/cablear/tomados
drwxrwxr-x root:root      /var/lib/ape/cablear/staging

usuarios de php-fpm:  root php-fpm8.3   ·   www-data php-fpm8.3
```

`/var/lib/ape/cablear` es **755 de root:root** y los subdirectorios **775 de root:root**. **`www-data` no es el dueño ni está en el grupo `root`, y no hay bit de escritura para otros: no puede escribir.** El endpoint lo detecta, lo dice con precisión y **no crea el ticket** — el diseño es fail-closed y correcto; lo que está mal es el despliegue.

> **El propio mensaje de error explica por qué se niega**: «el worker NO puede renombrar el ticket a tomados/ sin el; el ticket no se crea para no dejar un queued eterno». Preferir un 500 explicable a un ticket que se queda en `queued` para siempre es la decisión correcta.

**FIX REQUERIDO (una línea, fuera de mi alcance — `vps/` es out of scope):**

```bash
chown -R www-data:www-data /var/lib/ape/cablear
# o, si se prefiere conservar root como dueño:
chgrp -R www-data /var/lib/ape/cablear && chmod -R g+w /var/lib/ape/cablear
```

Hasta que eso se aplique, **nada se puede encolar en producción**: ni desde el panel, ni desde curl, ni desde el `.path`.

```text
{"ok":false,"error":"E_LISTA_NOMBRE_INVALIDO","motivo":"el nombre debe casar ^[A-Za-z0-9][A-Za-z0-9._-]{0,123}\\.m3u8$","auth":"heredada"}

```

Ambos rechazan **antes** de tocar la cola, así que estos dos sí se pueden verificar aunque la cola esté rota. El motivo es literal y sirve para el operador.

**Nota sobre el código de traversal:** el encolador devuelve `E_LISTA_NOMBRE_INVALIDO` (la regex del nombre lo caza) y **no** un código de traversal propio; el worker, en cambio, distingue y usa `E_LISTA_TRAVERSAL`. No es un fallo —se rechaza igual— pero el mismo ataque produce **dos códigos según la capa**.

## 6 · Hallazgos adicionales

1. **El core cambió después de t60.** t60 entregó `list_cablear_core.php` de **27.177 B / `107896b6…`**; hoy hay **29.415 B / `b8ea0d59…`** (+2.238 B). Verifiqué el de hoy.
2. **El listado reporta `bytes: 8`** para la lista del operador (`APE_LISTA_1794100720046`), con `bytes_gz: 352103394` y `bytes_descomprimidos: 1298723095`. No es un error del endpoint: **en disco hay un stub de 8 B y el contenido real viaja en el `.gz`**. Pero un operador que lea «8 bytes» para una lista de 1,3 GB se llevará una impresión falsa. Las dos listas grandes comparten `sha256 144659b4…` porque son **el mismo stub de 8 bytes** — coherente, y a la vez una trampa de lectura.
3. **`auth:"heredada"`** aparece en todas las respuestas. Es un campo del alias; no rompe nada, pero conviene saber que la respuesta lleva un campo de autenticación que no aporta estado.
4. **`device` tiene regex `^[A-Za-z0-9_-]{16,512}$`**: lo descubrí porque mi arnés mandó `device=generic` y recibí `400 E_DEVICE_INVALIDO` (D2 de t60 funcionando).
