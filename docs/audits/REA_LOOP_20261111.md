## 2. Los tres límites (de orquestación, no métricas)

| Límite | Valor | Cómo se aplica de verdad | ¿Se puede ejercer aquí? |
|---|---|---|---|
| `MAX_RETRIES_PER_GATE` | **3** | Cada gate se ejecuta hasta 3 veces; el `attempt_log` con exit y duración de cada intento queda en el estado. Un gate que falla 3 veces **detiene** el bucle | **Sí**, es el camino normal de fallo (C2) |
| `MAX_REMEDIATION_CYCLES` | **12** | Techo de ciclos que el llamador puede pedir: `--cycles > 12` → **exit 2** antes de ejecutar un solo gate. Un ciclo = una pasada completa por la lista | **Sí** (C3, `--cycles 13`) |
| `MAX_CONSECUTIVE_DEPLOY_FAILURES` | **2** | Se **lee** del estado (`consecutive_deploy_failures`) y si es ≥ 2 el bucle se niega a correr → **exit 2**. Lo incrementa el pipeline de despliegue, no este bucle | **Sí** por el lado de la lectura (C4); **NO_COMPUTADO** por el lado del incremento: este bucle no despliega, así que nunca lo sube |

**Declaración honesta sobre los ciclos:** sin un actuador de remediación (aquí no hay deploy ni reparación
automática), repetir un ciclo daría exactamente el mismo resultado. Por eso el bucle usa **un** ciclo y se
detiene en el primer fallo; `MAX_REMEDIATION_CYCLES` queda como techo duro de seguridad para cuando exista un
paso de remediación. No se finge que se consumen 12 ciclos.

## 3. Tres resultados por gate

| Resultado | Cuándo | ¿Detiene el bucle? | ¿Cuenta como PASS? |
|---|---|---|---|
| `PASS` | exit 0 | No | Sí |
| `FAIL` | exit != 0 tras agotar los 3 intentos, y **sin** firma declarada | **Sí** (los gates posteriores no se ejecutan) | No |
| `KNOWN_PREEXISTING` | exit != 0 **con la firma exacta declarada de antemano** en la tabla `KNOWN_PREEXISTING` | No | **No** — se reporta con su razón y su `id` (`KP1`) |

La firma de `KP1` exige las DOS cadenas a la vez (`[DEGRADA] IPTV_v5.4_MAX_AGGRESSION/vps/ape-jit/server.js`
y `TOTAL=8 PASS=7 FAIL=1`). Si el anti-degradation fallara por **otro** fichero o con otro recuento, la firma
no casa y el gate pasa a `FAIL` y detiene el bucle. Es una exención con cerradura, no un comodín.

**Detalle medido:** el gate G1 se reintenta igual 3 veces para que el conteo de intentos sea comparable entre
gates; la clasificación se aplica **después** de agotar los reintentos. Cuesta ~250 ms y evita un caso especial.

## 4. Códigos de salida

| Código | Significado |
|---|---|
| **0** | Todos los gates ejecutados `PASS` o `KNOWN_PREEXISTING` declarado |
| **1** | Algún gate `FAIL` tras agotar reintentos (incluye `E_GATE_MISSING` y `E_TIMEOUT`) |
| **2** | Límite de orquestación alcanzado: `E_CYCLE_LIMIT`, `E_CYCLE_LIMIT_INVALID` o `E_DEPLOY_FAILURE_LIMIT` |

## 6. Estado persistente

`docs/canary/state/rea_loop_state.json`, schema propio **`ape.canary.rea_loop.state.v1`**:

| Clave | Contenido |
|---|---|
| `schema`, `updated_at_utc`, `root` | identidad y momento |
| `limits` | los tres límites, escritos en el propio estado |
| `consecutive_deploy_failures` | contador leído del estado previo (lo alimenta el deploy) |
| `previous_state_schema` | prueba de que se releyó el estado anterior |
| `last_healthy` | última corrida **completa verde**. **Nunca** la sobrescribe una corrida fallida |
| `history` | `total_runs` / `healthy_runs` / `blocked_runs` / `failed_runs` |
| `runs[]` | últimas 20 corridas; cada una con `gates[]` (`id`, `name`, `command`, `attempts`, `attempt_log[]`, `exit_code`, `duration_ms`, `result`, `known_preexisting`, `observations`, `output_excerpt`) y `block` si lo hubo |

Al arrancar se **lee** el estado anterior y se **añade** la corrida nueva: la historia no se pierde. Cuando
una corrida falla, el `run` guarda `last_healthy_kept: <run_id>` para que quede explícito **cuál** se conservó.

## 8. "No despliega, no red, no VPS": cómo se comprueba

- `require()` del fichero: **solo** `fs`, `path` y `child_process` (líneas 27-29). Cero dependencias.
- Único `spawnSync` (línea 99): lanza `process.execPath` con la ruta absoluta del gate declarado. No hay
  `shell: true`, así que no se interpreta ninguna cadena de shell.
- Barrido de tokens sobre el código: `http` 0, `curl` 0, `ssh` 0, `scp` 0, `fetch(` 0, `net.` 0, `dgram` 0,
  `systemctl` 0, `deploy.sh` 0, `178.156` 0, `duckdns` 0.
- `VPS` aparece **2 veces fuera de comentarios**, y ambas son **texto dentro de la tabla
  `KNOWN_PREEXISTING`**: la ruta `IPTV_v5.4_MAX_AGGRESSION/vps/ape-jit/server.js` (que es la salida literal
  del gate G1, necesaria para casar la firma) y su razón. Ninguna es una llamada.
- El bucle escribe **solo** su fichero de estado (y crea su directorio). Los gates, por su cuenta, pueden
  escribir en `os.tmpdir()` — `test_playlist_adapter.js` lo hace y lo declara en su salida — eso no lo
  controla este bucle y no se le atribuye.
